<feature>
  <name>AppointmentService — Status Machine + Available Slots</name>
  <files>backend/src/services/appointment.service.ts, backend/tests/services/appointment.service.test.ts</files>
  <behavior>
  **Status machine transitions (SCHD-04):**
  - pending -> confirmed: VALID (confirmAppointment)
  - pending -> cancelled: VALID (cancelAppointment)
  - confirmed -> completed: VALID (completeAppointment)
  - confirmed -> cancelled: VALID (cancelAppointment)
  - confirmed -> no_show: VALID (markNoShow)
  - completed -> anything: INVALID (422 INVALID_STATUS_TRANSITION)
  - cancelled -> anything: INVALID (422 INVALID_STATUS_TRANSITION)
  - no_show -> anything: INVALID (422 INVALID_STATUS_TRANSITION)

  **Create appointment (SCHD-02):**
  - Valid input with available slot -> creates with status 'pending', end_time = start_time + duration_minutes + buffer_minutes
  - Time outside working hours -> 422 OUTSIDE_WORKING_HOURS (SCHD-05)
  - Time conflicts with existing appointment -> 409 TIME_SLOT_TAKEN (from repository constraint)
  - Time conflicts with blocked slot -> 422 TIME_SLOT_BLOCKED

  **Available slots (SCHD-01, SCHD-05):**
  - Professional with working_hours 09:00-18:00, service 60min -> returns slots 09:00, 10:00, ..., 17:00
  - Existing appointment at 10:00-11:00 -> slot 10:00 excluded
  - Blocked slot at 14:00-15:00 -> slot 14:00 excluded
  - Service with 30min buffer -> appointment at 10:00-11:30 (60min + 30min buffer) blocks 10:00 and 11:00
  - Professional not working on requested day -> returns empty array
  - Recurring absence active on date -> corresponding slots excluded
  - Recurring absence with date excluded -> slots NOT excluded (exception)

  **Complete appointment (SCHD-04):**
  - With payment data -> records payment alongside status change (amount, method stored)
  - Without payment data -> just changes status to completed

  **List appointments (SCHD-01):**
  - By date -> returns appointments for that date ordered by start_time
  - By date range -> returns appointments in range
  - Filters by professional_id, status work correctly
  - Multi-tenant: studio A cannot see studio B appointments
  </behavior>
  <implementation>
  Create AppointmentService class with constructor injection: AppointmentRepository, BlockedSlotService, ProfessionalRepository (for working_hours), ServiceRepository (for duration/buffer).

  VALID_TRANSITIONS map defines the state machine. Each transition method (confirm, complete, cancel, noShow) does: getById -> validate transition -> repo.updateStatus.

  createAppointment: validate working hours -> calculate end_time (start + duration + buffer) -> check blocked slots -> repo.create (constraint catches concurrent conflicts).

  getAvailableSlots: get professional working_hours for day -> generate all possible slots at 15-min intervals -> fetch existing appointments for date -> fetch expanded blocked slots for date -> filter out overlapping slots.

  completeAppointment: validate transition -> if payment provided, create payment record -> repo.updateStatus. Payment recording is a simple INSERT into a payments-adjacent column or future payments table. For Phase 3, store payment_amount and payment_method directly on the appointment row (add columns in migration if not present, or use a separate payments table if it exists in schema).

  Note: Check if a `payments` table exists in 001_initial_schema.sql. If yes, use it. If not, add payment_amount (integer, cents) and payment_method (text) columns to the appointments table via a new migration task in this plan.
  </implementation>
</feature>

<feature>
  <name>BlockedSlotService — Recurrence Expansion</name>
  <files>backend/src/services/blocked-slot.service.ts, backend/tests/services/blocked-slot.service.test.ts</files>
  <behavior>
  **Recurrence expansion (SCHD-03):**
  - Sporadic absence on 2026-04-05 queried for 2026-04-05 -> returned
  - Sporadic absence on 2026-04-05 queried for 2026-04-06 -> NOT returned
  - Recurring weekly [1,3] (Mon,Wed) queried for a Monday -> returned
  - Recurring weekly [1,3] queried for a Tuesday -> NOT returned
  - Recurring with until=2026-04-10 queried for 2026-04-15 -> NOT returned
  - Recurring with excluded_dates=['2026-04-07'] queried for 2026-04-07 -> NOT returned
  - Recurring with no until (null) queried for any matching day -> returned

  **Create absence (SCHD-03):**
  - Sporadic: creates with date, start_time, end_time, title, no recurrence_rule
  - Recurring: creates with recurrence_rule JSONB, title
  - Title is required (enforced by Zod)

  **Delete absence (SCHD-03):**
  - Sporadic: hard delete
  - Recurring single occurrence: addExcludedDate (does not delete the rule)
  - Recurring all: hard delete

  **Get expanded for date (used by AppointmentService):**
  - Returns all time ranges blocked on a specific date for a professional
  - Combines sporadic absences on that date + recurring rules active on that date
  - Excludes dates in excluded_dates array
  </behavior>
  <implementation>
  Create BlockedSlotService with constructor injection: BlockedSlotRepository.

  `getExpandedForDate(studioId, professionalId, date)`: query repo for all blocked_slots for professional where (date matches for sporadic) OR (recurrence_rule IS NOT NULL). Then filter in-memory: for recurring rules, check isRecurrenceActiveOnDate(rule, date, excluded_dates). Return array of {start_time, end_time} ranges.

  `isRecurrenceActiveOnDate(rule, date, excludedDates)`: return false if date in excludedDates, false if rule.until and date > until, false if day of week not in rule.days. Otherwise true.

  `create(studioId, input)`: validate professional belongs to studio -> repo.create.
  `delete(studioId, id)`: repo.delete.
  `removeOccurrence(studioId, id, date)`: repo.addExcludedDate.
  </implementation>
</feature>
